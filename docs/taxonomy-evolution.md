# Taxonomy Evolution and Complaint Intelligence

## 1. Purpose

The Support Ticket Resolution Assistant uses structured complaint intelligence before retrieval and resolution generation.

The intelligence layer extracts:

- Intent
- Sub-intent
- Product
- Severity
- Sentiment
- Entities
- Confidence
- Model version

This structured representation helps the system understand the complaint before searching historical conversations and knowledge-base evidence.

---

## 2. Current Taxonomy

The current top-level intent taxonomy is intentionally controlled.

```text
Connectivity
Mobile
Billing
Account
Outage
Other
```

The implementation represents these values using a controlled enum:

```python
class Intent(StrEnum):
    CONNECTIVITY = "Connectivity"
    MOBILE = "Mobile"
    BILLING = "Billing"
    ACCOUNT = "Account"
    OUTAGE = "Outage"
    OTHER = "Other"
```

Using a controlled top-level taxonomy prevents uncontrolled variation in the most important routing dimension.

---

## 3. Sub-Intent

Sub-intents are represented as strings rather than a fixed enum.

For example, a broadband complaint can produce:

```
Intermittent broadband drop
```

This design intentionally allows the taxonomy to evolve without requiring a code change for every new sub-intent.

**Example hierarchy:**

```
Connectivity
    ├── Intermittent broadband drop
    ├── Slow broadband
    ├── No broadband connection
    └── Wi-Fi connectivity issue
```

The exact sub-intent vocabulary can evolve as more support data becomes available.

---

## 4. Product Taxonomy

Product is also represented as a string. Examples include:

```
Broadband
Mobile
```

A future production taxonomy could introduce a more structured product hierarchy:

```
Telecom
├── Broadband
│   ├── Fiber
│   ├── DSL
│   └── Fixed Wireless
│
└── Mobile
    ├── Voice
    ├── SMS
    └── Mobile Data
```

The current implementation keeps this field flexible because the available dataset does not provide a sufficiently reliable product taxonomy for every historical conversation.

---

## 5. Severity

Severity uses a controlled enum:

```
LOW
MEDIUM
HIGH
CRITICAL
UNKNOWN
```

Severity helps distinguish ordinary troubleshooting requests from complaints that may require faster intervention.

**Example:**

> "My broadband drops every evening and I cannot work."

→ Severity: `HIGH`

> **Note:** Severity should not be treated as an absolute business priority without considering operational escalation rules.

---

## 6. Sentiment

Sentiment uses:

```
POSITIVE
NEUTRAL
NEGATIVE
UNKNOWN
```

Sentiment provides additional context about the customer's experience.

**Example:**

> "My broadband keeps disconnecting and this is costing me money."

→ Sentiment: `NEGATIVE`

Sentiment is primarily contextual rather than a direct escalation rule.

---

## 7. Entities

Entities are represented as a flexible dictionary:

```python
entities: dict[str, str]
```

This allows the intelligence layer to capture useful complaint-specific information without requiring every possible entity type to be encoded into the schema.

**Example:**

```json
{
  "drop_time": "20:00",
  "device": "router"
}
```

For the representative broadband complaint, the system extracted:

- `drop_time` = `20:00`
- `device` = `router`

These entities can provide useful signals for retrieval and resolution generation.

---

## 8. Confidence

Complaint intelligence includes a confidence value:

```
0.0 <= confidence <= 1.0
```

**Example:** `confidence = 0.94`

Confidence is useful for monitoring and future routing decisions. A future production implementation could use confidence thresholds such as:

| Confidence Level | Behaviour |
|---|---|
| High | Normal retrieval and resolution |
| Medium | Broader retrieval / additional evidence |
| Low | Clarification or escalation |

> **Note:** The current system does not implement this complete confidence-based routing policy.

---

## 9. Model Version

Every intelligence result includes a model version, e.g.:

```
llm-intelligence-v1
```

This allows future evaluation to distinguish results generated by different intelligence implementations, particularly when the taxonomy or extraction prompt changes.

---

## 10. Why the Taxonomy Is Hybrid

The current schema intentionally combines controlled and flexible fields:

| Type | Fields |
|---|---|
| **Controlled** | Intent, Severity, Sentiment |
| **Flexible** | Sub-intent, Product, Entities |

This provides a balance between consistency, extensibility, implementation simplicity, and future taxonomy growth.

- A **completely fixed** taxonomy provides strong consistency but makes evolution expensive.
- A **completely free-form** taxonomy makes aggregation, monitoring, and routing unreliable.

The hybrid approach controls values where consistency is most important while allowing domain-specific categories to evolve.

## 12. Taxonomy and Retrieval

Complaint intelligence influences retrieval by providing structured context. Semantic retrieval handles linguistic variation — for example:

- `"My broadband keeps cutting out every night."`
- `"Internet connection drops around 8 PM every evening."`

…describe the same underlying issue. The taxonomy adds structure:

```
Intent:     Connectivity
Sub-intent: Intermittent broadband drop
Product:    Broadband
```

Structured intelligence and semantic retrieval provide complementary signals.

---

## 13. Taxonomy and Resolution

The extracted taxonomy also provides context to the resolution service:

```
Intent     → Connectivity
Sub-intent → Intermittent broadband drop
Product    → Broadband
Severity   → HIGH
Sentiment  → NEGATIVE
```

> **Important:** The taxonomy does not replace evidence. The resolution prompt explicitly treats authoritative knowledge-base evidence as the primary source for troubleshooting recommendations.

---

## 14. Taxonomy Evolution Strategy

Taxonomy changes should be evidence-driven:

```
Support Conversations
        ↓
Aggregate Complaint Patterns
        ↓
Identify Repeated Categories
        ↓
Propose Taxonomy Change
        ↓
Evaluate Against Historical Data
        ↓
Version Taxonomy
        ↓
Deploy
        ↓
Monitor
```

This prevents taxonomy changes from being driven by individual examples only.

---

## 15. When to Introduce a New Sub-Intent

A new sub-intent should be considered when an issue:

- Occurs repeatedly
- Represents a meaningful operational distinction
- Has different troubleshooting or escalation behaviour
- Improves reporting or routing
- Cannot be adequately represented by an existing category

**Example:** If many complaints repeatedly identify evening-only broadband failures, the system could distinguish `Intermittent broadband drop` from a more specific `Scheduled/evening broadband degradation` — but only after validating that the distinction is operationally useful.

---

## 16. Avoiding Taxonomy Explosion

A major risk is creating too many highly specific categories. For example, these should **not** automatically become separate categories:

```
Drops at 7 PM
Drops at 8 PM
Drops at 9 PM
Drops after dinner
Drops every evening
```

A better approach:

```
Sub-intent: Intermittent broadband drop
Entity:     drop_time = 20:00
```

This preserves useful information without unnecessarily expanding the taxonomy.

---

## 17. Entity vs Taxonomy Decision

> **Design principle:** Use taxonomy for stable business categories and entities for variable complaint details.

| Type | Example |
|---|---|
| Stable category | `Connectivity` |
| Stable sub-intent | `Intermittent broadband drop` |
| Variable entity | `drop_time = 20:00`, `device = router` |

This keeps the taxonomy compact while retaining important complaint-specific information.

---

## 18. Handling Unknown Categories

The top-level taxonomy includes `Other`, and severity/sentiment include `UNKNOWN`. These provide a safe representation when the system cannot confidently classify a complaint.

> The system should **not** force an uncertain complaint into an unrelated category merely to avoid an unknown value.

Future production behaviour could route low-confidence or unknown classifications toward broader retrieval, clarification, manual review, or escalation.

---

## 19. Taxonomy Quality Evaluation

Taxonomy evolution should be evaluated separately from retrieval evaluation. Useful classification metrics include:

- Intent accuracy / Intent macro-F1
- Sub-intent accuracy
- Product accuracy
- Severity macro-F1
- Sentiment macro-F1
- Entity extraction precision / recall

> **Note:** Evaluation should use a manually reviewed dataset with expected labels. Classification metrics should **not** be inferred from the current retrieval evaluation set, which is designed to evaluate retrieval quality.

---

## 20. Taxonomy Versioning

Production taxonomy changes should be versioned:

```
taxonomy-v1
taxonomy-v2
taxonomy-v3
```

A version should change when a category is added or removed, category definitions change, labels are renamed, or routing behaviour changes. Versioning keeps historical monitoring interpretable — for example, `llm-intelligence-v1` + `taxonomy-v2` allows future analysis to separate model changes from taxonomy changes.

---

## 21. Backward Compatibility

Changing taxonomy categories can affect:

- Historical analytics and dashboards
- Retrieval filters and escalation rules
- Reports and downstream integrations

Production taxonomy changes should therefore consider backward compatibility. Historical records should not be silently rewritten without preserving the taxonomy version under which they were generated.

---

## 22. Human Review Loop

Support-agent feedback can provide an important source of taxonomy improvement:

```
Generated Intelligence
        ↓
Support Agent Review
        ↓
  ┌─────┴─────┐
Correct    Incorrect
               ↓
        Correction Data
               ↓
       Taxonomy Analysis
```

Repeated corrections can reveal missing or ambiguous categories, incorrect classification patterns, entity types that need to be added, and escalation cases that require new distinctions.

---

## 23. Taxonomy Drift Monitoring

Taxonomy distributions should be monitored over time. Example distribution:

| Intent | Share |
|---|---|
| Connectivity | 52% |
| Mobile | 21% |
| Billing | 14% |
| Account | 8% |
| Outage | 4% |
| Other | 1% |

> *Percentages above are illustrative.*

A sudden change in distribution may indicate a change in customer behaviour, a new outage, a product change, a model regression, a prompt change, or a taxonomy change. Distribution monitoring complements individual classification evaluation.

---

## 24. Production Taxonomy Roadmap

| Phase | Focus |
|---|---|
| **Phase 1 — Current** | Controlled intent, flexible sub-intent/product, controlled severity/sentiment, flexible entities |
| **Phase 2 — Standardisation** | Validated sub-intent/product vocabulary, entity normalisation, taxonomy versioning |
| **Phase 3 — Operational integration** | Classification-aware routing, confidence thresholds, escalation policies, agent feedback |
| **Phase 4 — Continuous evolution** | Taxonomy drift monitoring, human-reviewed corrections, automated candidate categories, offline evaluation, controlled rollout |

---

## 25. Design Principles

1. **Keep high-level categories controlled** — Important routing dimensions should use stable enumerated values.
2. **Keep variable details flexible** — Complaint-specific details should be represented as entities rather than creating excessive categories.
3. **Let evidence drive evolution** — New categories should be supported by repeated operational patterns.
4. **Avoid taxonomy explosion** — Do not create a new category for every minor variation of the same problem.
5. **Version changes** — Taxonomy and model changes should be traceable.
6. **Preserve uncertainty** — Unknown or low-confidence cases should remain identifiable rather than being incorrectly forced into a category.
7. **Evaluate before deployment** — Taxonomy changes should be tested against representative historical data before production rollout.

---

## 26. Conclusion

The current complaint intelligence schema provides a practical foundation for structured telecom support understanding. It combines:

- Controlled taxonomy (intent, severity, sentiment)
- Flexible sub-intents and entities
- Confidence scoring
- Model versioning

This allows the system to capture meaningful complaint structure without creating an unnecessarily rigid taxonomy.

The most important future evolution is not simply adding more categories — it is creating a **controlled feedback loop** in which support data, human corrections, classification evaluation, retrieval behaviour, and operational outcomes guide taxonomy changes. This approach allows the taxonomy to become more useful over time while remaining explainable, versioned, and operationally manageable.
