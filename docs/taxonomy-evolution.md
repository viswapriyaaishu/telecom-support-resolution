# Taxonomy Evolution and Complaint Intelligence

## 1. Purpose

The Support Ticket Resolution Assistant uses structured complaint intelligence before retrieval and resolution generation.

The intelligence layer extracts:

- Intent
- Sub-intent
- Product
- Severity
- Sentiment
- Entities
- Confidence
- Model version

This structured representation helps the system understand the complaint before searching historical conversations and knowledge-base evidence.

---

## 2. Current Taxonomy

The current top-level intent taxonomy is intentionally controlled.

```text
Connectivity
Mobile
Billing
Account
Outage
Other

The implementation represents these values using a controlled enum.

class Intent(StrEnum):
    CONNECTIVITY = "Connectivity"
    MOBILE = "Mobile"
    BILLING = "Billing"
    ACCOUNT = "Account"
    OUTAGE = "Outage"
    OTHER = "Other"

Using a controlled top-level taxonomy prevents uncontrolled variation in the most important routing dimension.

3. Sub-Intent

Sub-intents are represented as strings rather than a fixed enum.

For example, a broadband complaint can produce:

Intermittent broadband drop

This design intentionally allows the taxonomy to evolve without requiring a code change for every new sub-intent.

Example hierarchy:

Connectivity
    ├── Intermittent broadband drop
    ├── Slow broadband
    ├── No broadband connection
    └── Wi-Fi connectivity issue

The exact sub-intent vocabulary can evolve as more support data becomes available.

4. Product Taxonomy

Product is also represented as a string.

Examples include:

Broadband
Mobile

A future production taxonomy could introduce a more structured product hierarchy:

Telecom
├── Broadband
│   ├── Fiber
│   ├── DSL
│   └── Fixed Wireless
│
└── Mobile
    ├── Voice
    ├── SMS
    └── Mobile Data

The current implementation keeps this field flexible because the available dataset does not provide a sufficiently reliable product taxonomy for every historical conversation.

5. Severity

Severity uses a controlled enum:

LOW
MEDIUM
HIGH
CRITICAL
UNKNOWN

Severity helps distinguish ordinary troubleshooting requests from complaints that may require faster intervention.

For example:

Customer:
"My broadband drops every evening and I cannot work."

Possible severity:
HIGH

Severity should not be treated as an absolute business priority without considering operational escalation rules.

6. Sentiment

Sentiment uses:

POSITIVE
NEUTRAL
NEGATIVE
UNKNOWN

Sentiment provides additional context about the customer's experience.

For example:

"My broadband keeps disconnecting and this is costing me money."

Sentiment:
NEGATIVE

Sentiment is primarily contextual rather than a direct escalation rule.

7. Entities

Entities are represented as a flexible dictionary:

entities: dict[str, str]

This allows the intelligence layer to capture useful complaint-specific information without requiring every possible entity type to be encoded into the schema.

Example:

{
  "drop_time": "20:00",
  "device": "router"
}

For the representative broadband complaint, the system extracted:

drop_time = 20:00
device = router

These entities can provide useful signals for retrieval and resolution generation.

8. Confidence

Complaint intelligence includes a confidence value:

0.0 <= confidence <= 1.0

Example:

confidence = 0.94

Confidence is useful for monitoring and future routing decisions.

A future production implementation could use confidence thresholds such as:

High confidence
    ↓
Normal retrieval and resolution

Medium confidence
    ↓
Broader retrieval / additional evidence

Low confidence
    ↓
Clarification or escalation

The current system does not implement this complete confidence-based routing policy.

9. Model Version

Every intelligence result includes a model version.

Example:

llm-intelligence-v1

This allows future evaluation to distinguish results generated by different intelligence implementations.

For example:

llm-intelligence-v1
llm-intelligence-v2

could be compared against the same evaluation set.

Model versioning is particularly important when the taxonomy or extraction prompt changes.

10. Why the Taxonomy Is Hybrid

The current schema intentionally combines controlled and flexible fields.

Controlled
├── Intent
├── Severity
└── Sentiment

Flexible
├── Sub-intent
├── Product
└── Entities

This provides a balance between:

consistency
extensibility
implementation simplicity
future taxonomy growth

A completely fixed taxonomy would provide strong consistency but make taxonomy evolution expensive.

A completely free-form taxonomy would make aggregation, monitoring, and routing unreliable.

The hybrid approach provides controlled values where consistency is most important while allowing domain-specific categories to evolve.

12. Taxonomy and Retrieval

Complaint intelligence can influence retrieval by providing structured context.

The original complaint contains natural-language variation.

For example:

"My broadband keeps cutting out every night."

and:

"Internet connection drops around 8 PM every evening."

may describe the same underlying issue.

Semantic retrieval handles linguistic variation.

The taxonomy provides additional structure:

Intent:
Connectivity

Sub-intent:
Intermittent broadband drop

Product:
Broadband

Together, structured intelligence and semantic retrieval provide complementary signals.

13. Taxonomy and Resolution

The extracted taxonomy also provides context to the resolution service.

For example:

Intent       → Connectivity
Sub-intent   → Intermittent broadband drop
Product      → Broadband
Severity     → HIGH
Sentiment    → NEGATIVE

This helps the resolution process understand what type of issue is being addressed.

However, the taxonomy does not replace evidence.

The resolution prompt explicitly treats authoritative knowledge-base evidence as the primary source for troubleshooting recommendations.

14. Taxonomy Evolution Strategy

Taxonomy changes should be evidence-driven.

A proposed evolution process is:

Support Conversations
        |
        v
Aggregate Complaint Patterns
        |
        v
Identify Repeated Categories
        |
        v
Propose Taxonomy Change
        |
        v
Evaluate Against Historical Data
        |
        v
Version Taxonomy
        |
        v
Deploy
        |
        v
Monitor

This prevents taxonomy changes from being driven only by individual examples.

15. When to Introduce a New Sub-Intent

A new sub-intent should be considered when an issue:

occurs repeatedly,
represents a meaningful operational distinction,
has different troubleshooting or escalation behavior,
improves reporting or routing,
or cannot be adequately represented by an existing category.

For example, if many complaints repeatedly identify evening-only broadband failures, the system could distinguish:

Intermittent broadband drop

from a more specific category such as:

Scheduled/evening broadband degradation

Only after validating that the distinction is operationally useful should such a category be added.

16. Avoiding Taxonomy Explosion

A major risk is creating too many highly specific categories.

For example, these should not automatically become separate categories:

Drops at 7 PM
Drops at 8 PM
Drops at 9 PM
Drops after dinner
Drops every evening

These may represent the same underlying issue.

A better approach is:

Sub-intent:
Intermittent broadband drop

Entity:
drop_time = 20:00

This preserves useful information without unnecessarily expanding the taxonomy.

17. Entity vs Taxonomy Decision

A useful design principle is:

Use taxonomy for stable business categories and entities for variable complaint details.

For example:

Stable category:
Connectivity

Stable sub-intent:
Intermittent broadband drop

Variable entity:
drop_time = 20:00

Similarly:

Stable category:
Connectivity

Variable entity:
device = router

This keeps the taxonomy compact while retaining important information.

18. Handling Unknown Categories

The top-level taxonomy contains:

Other

and severity/sentiment contain:

UNKNOWN

These values provide a safe representation when the system cannot confidently classify a complaint.

The system should not force an uncertain complaint into an unrelated category merely to avoid an unknown value.

Future production behavior could route low-confidence or unknown classifications toward:

broader retrieval,
clarification,
manual review,
or escalation.
19. Taxonomy Quality Evaluation

Taxonomy evolution should be evaluated separately from retrieval evaluation.

Useful classification metrics include:

Intent accuracy
Intent macro-F1
Sub-intent accuracy
Product accuracy
Severity macro-F1
Sentiment macro-F1
Entity extraction precision
Entity extraction recall

Evaluation should use a manually reviewed dataset with expected labels.

The current repository's retrieval golden set is designed to evaluate retrieval quality rather than provide a complete taxonomy classification benchmark.

Therefore, classification metrics should not be inferred from the current retrieval evaluation.

20. Taxonomy Versioning

Production taxonomy changes should be versioned.

Example:

taxonomy-v1
taxonomy-v2
taxonomy-v3

A version should change when:

a category is added,
a category is removed,
category definitions change,
labels are renamed,
routing behavior changes.

Versioning makes historical monitoring interpretable.

For example:

Model:
llm-intelligence-v1

Taxonomy:
taxonomy-v2

allows future analysis to determine whether a change in classification behavior was caused by the model or taxonomy.

21. Backward Compatibility

Changing taxonomy categories can affect:

historical analytics,
dashboards,
retrieval filters,
escalation rules,
reports,
downstream integrations.

Therefore, production taxonomy changes should consider backward compatibility.

A category migration can use mappings such as:

Old category
     |
     v
Migration mapping
     |
     v
New category

Historical records should not be silently rewritten without preserving the taxonomy version under which they were generated.

22. Human Review Loop

Support-agent feedback can provide an important source of taxonomy improvement.

A future workflow could be:

Generated Intelligence
        |
        v
Support Agent Review
        |
        +---- Correct
        |
        +---- Incorrect
                 |
                 v
          Correction Data
                 |
                 v
        Taxonomy Analysis

Repeated corrections can reveal:

missing categories,
ambiguous categories,
incorrect classification patterns,
entity types that need to be added,
escalation cases that require new distinctions.

This creates a feedback loop between the production system and taxonomy design.

23. Taxonomy Drift Monitoring

Taxonomy distributions should be monitored over time.

For example:

Connectivity     52%
Mobile           21%
Billing          14%
Account           8%
Outage            4%
Other             1%

A sudden change in distribution may indicate:

an actual change in customer behavior,
a new outage,
a product change,
a model regression,
a prompt change,
or a taxonomy change.

Distribution monitoring therefore complements individual classification evaluation.

The percentages above are illustrative and are not claimed as measurements from the current dataset.

25. Design Principles

The taxonomy design follows several principles.

1. Keep high-level categories controlled

Important routing dimensions should use stable enumerated values.

2. Keep variable details flexible

Complaint-specific details should be represented as entities rather than creating excessive categories.

3. Let evidence drive evolution

New categories should be supported by repeated operational patterns.

4. Avoid taxonomy explosion

Do not create a new category for every minor variation of the same problem.

5. Version changes

Taxonomy and model changes should be traceable.

6. Preserve uncertainty

Unknown or low-confidence cases should remain identifiable rather than being incorrectly forced into a category.

7. Evaluate before deployment

Taxonomy changes should be tested against representative historical data before production rollout.

26. Conclusion

The current complaint intelligence schema provides a practical foundation for structured telecom support understanding.

It combines:

Controlled taxonomy
        +
Flexible sub-intents
        +
Flexible entities
        +
Confidence
        +
Model versioning

This allows the system to capture meaningful complaint structure without creating an unnecessarily rigid taxonomy.

The most important future evolution is not simply adding more categories. It is creating a controlled feedback loop in which support data, human corrections, classification evaluation, retrieval behavior, and operational outcomes guide taxonomy changes.

This approach allows the taxonomy to become more useful over time while remaining explainable, versioned, and operationally manageable.
